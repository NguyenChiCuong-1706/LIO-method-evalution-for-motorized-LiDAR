# MHF9025-V3 speed feedback and PID assessment

## Recorded 90 RPM session

The offline analyzer uses only rows whose fresh response starts with `0x9C` or
`0x92`. It excludes the first 0.5 s and does not count cached values in `0x9A`
or other rows. Results for `motor_session_20261030T083514061588Z.csv` are:

| Estimate | Samples | Mean RPM | MAE RPM | SD RPM | Range RPM |
|---|---:|---:|---:|---:|---:|
| Raw `0x9C` | 73 | 90.242 | 2.297 | 2.821 | 82.500–96.667 |
| 0.25 s low-pass display | 73 | 89.965 | 1.166 | 1.519 | 84.942–92.805 |
| Successive `0x92` angle | 89 | 90.062 | 0.272 | 0.461 | 88.402–91.851 |

The angle intervals average 0.10555 s and range from 0.09976 to 0.11246 s.
The legacy CSV records host receive times but not exchange round-trip times, so
controller latency cannot be bounded retrospectively. New logs use the midpoint
of each measured exchange interval and record the sum of the adjacent half-RTT
values as host timing uncertainty. Undocumented controller processing latency
still remains unknown.

The much smoother angle-derived average supports velocity measurement noise or
quantization in `0x9C` more strongly than actual large shaft-speed oscillation.
It does not prove this physically: both values are generated by the same motor
controller. The mean errors are small, and the dataset does not show a material
steady-state offset. Startup behavior is separated by the 0.5 s exclusion.
Independent marker/video measurement is still needed to distinguish actual
controller oscillation from internal estimator noise.

## PID assessment

The available V2.35 layout describes `0x30` as six raw angle, speed, and torque
PI readback bytes, `0x31` as a RAM write, and `0x32` as a ROM write. Compatibility
with MHF9025-V3 is unverified, and actual `0x30` requests to this motor timed
out. Therefore the existing parameter values are unknown and PID tuning is not
justified by this recording. The GUI exposes only the read attempt and cannot
send either write command.

Before any tuning proposal, obtain V3 documentation or a verified LK Motor Tool
readout, confirm the existing parameters without changing them, repeat several
steady-state trials with independent shaft video, and show a repeatable physical
oscillation or steady-state error. Only then define one-parameter, small-step
changes with a recorded baseline, fixed load and supply, rollback values, and
the existing STOP/DISABLE and independent cutoff procedure.

## STOP_UNCONFIRMED

The old 90 RPM CSV ends at 10.120 s with raw speed zero and state
`STOP_UNCONFIRMED`. The old logger did not save STOP/DISABLE acknowledgements or
the three individual post-stop `0x9C` verification samples, so the exact failed
condition cannot be recovered from that CSV. A zero final CAN speed alone cannot
establish physical stopping. The final encoder differs from the last logged
running speed row, which is consistent with motion during the stop interval but
does not identify which cleanup check failed.

New logs save both acknowledgements, every `VERIFY_STOP` speed/encoder response,
the combined controller-zero result, and `physical_stop_verified=False`.
`STOP_UNCONFIRMED` remains the result if either acknowledgement or the bounded
three-sample controller check fails. Independent power cutoff remains required.
